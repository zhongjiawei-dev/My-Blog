界面显示正确，数据库却对不上：SQL 核对的四个切入点

2026-09-26 约 7 分钟 MySQL · JOIN

在 P2P 借贷项目里，我遇到过一个很典型的问题：用户完成还款后，页面显示的「待还金额」变成了 0， 提示「还款成功」，一切看起来都正常。但账户流水表里只记录了 1 条记录，应该有 2 条 —— 本金和利息被合并成了一笔，导致对账时金额对不上。

这类缺陷靠界面永远测不出来。界面校验的是「展示逻辑」，数据库校验的是「业务事实」。 这篇整理我做数据库验证时的四个切入点，都基于 MySQL。

切入点一：金额一致性 —— 主表与流水表要对得上

金融类系统的金额通常存在两处：业务主表（订单、标的）记录「应是多少」，流水表记录「实际动了多少」。 两者必须相等，这是最值得写 SQL 去卡的地方。 

-- 找出「订单金额 ≠ 流水合计」的异常单
SELECT
    o.id            AS order_id,
    o.amount        AS order_amount,
    IFNULL(SUM(f.amount), 0) AS flow_amount
FROM t_order o
LEFT JOIN t_account_flow f
       ON f.order_id = o.id
      AND f.flow_type IN ('REPAY_PRINCIPAL', 'REPAY_INTEREST')
WHERE o.status = 'REPAID'
GROUP BY o.id, o.amount
HAVING o.amount <> IFNULL(SUM(f.amount), 0);
💡
为什么用 LEFT JOIN 而不是 INNER JOIN：如果某笔订单根本没有流水（漏记）， INNER JOIN 会把它直接过滤掉，异常就被隐藏了。LEFT JOIN + IFNULL 才能把「没有流水」这种更严重的缺陷暴露出来。

切入点二：状态机 —— 有没有非法流转

借贷业务的状态是有限的：待审核 → 已流标 / 已满标 → 还款中 → 已结清。 如果出现「待审核」直接跳到「已结清」，说明某条分支漏了校验。

我会把合法流转写成一张对照表，再用 SQL 找出不在表里的记录。简单场景可以直接用 CASE WHEN： 

-- 找出状态与时间字段矛盾的订单
SELECT id, status, audit_time, full_time, repay_time
FROM t_loan
WHERE
   (status = 'FULL'      AND full_time  IS NULL)      -- 已满标却没有满标时间
OR (status = 'REPAYING'  AND full_time  IS NULL)      -- 还款中却没满标
OR (status = 'FINISHED'  AND repay_time IS NULL)      -- 已结清却没结清时间
OR (status = 'REJECTED'  AND audit_time IS NULL);     -- 已拒绝却无审核记录

这个写法有个好处：它不依赖业务代码，只依赖「状态和字段在语义上是否自洽」。 写一次，之后每轮回归都能直接跑。

切入点三：重复与幂等 —— 同一个操作被记了几次

接口超时重试、用户连点两下、消息队列重投，都会造成重复写入。 测试时我会在关键动作前后各查一次计数： 

-- 同一订单、同一类型，是否被重复记账
SELECT order_id, flow_type, COUNT(*) AS cnt
FROM t_account_flow
GROUP BY order_id, flow_type
HAVING COUNT(*) > 1;

-- 同一用户同一秒内的重复借款申请
SELECT user_id, DATE_FORMAT(create_time, '%Y-%m-%d %H:%i:%s') AS sec, COUNT(*) AS cnt
FROM t_loan
GROUP BY user_id, sec
HAVING COUNT(*) > 1;

第二条 SQL 是我在验证「重复提交」用例时写的。当时接口层面没有拦截，连点两次就生成两笔借款单 —— 这个缺陷如果只看页面，两次跳转都正常，根本发现不了。

切入点四：孤儿数据 —— 关联表里有没有断链

删除、回滚、事务不完整都会留下「父记录没了、子记录还在」的脏数据。用反连接（LEFT JOIN ... IS NULL） 一次就能扫出来： 

-- 流水表里存在、但对应订单已不存在的记录
SELECT f.*
FROM t_account_flow f
LEFT JOIN t_order o ON o.id = f.order_id
WHERE o.id IS NULL;

-- 标的已存在，但没有任何投资记录（僵尸标的）
SELECT l.id, l.title
FROM t_loan l
LEFT JOIN t_invest i ON i.loan_id = l.id
WHERE i.id IS NULL AND l.status = 'FULL';

把 SQL 沉淀成回归脚本

这四个切入点我最后整理成了一份 sql_check.sql，按「金额 / 状态 / 重复 / 孤儿」分四段。 每轮回归跑完业务用例后执行一次，有结果就是异常，不需要人工判断。

检查项异常信号常见根因
金额一致性主表金额 ≠ 流水合计少记一条流水、四舍五入方式不一致
状态机状态与时间字段矛盾分支漏校验、并发下状态覆盖
重复记账同订单同类流水 > 1 条接口未做幂等、重试机制缺陷
孤儿数据关联表查不到父记录删除未级联、事务未回滚

这样做还有个额外收益：提缺陷时可以直接把 SQL 和结果截图贴进去，开发看一眼就知道去查哪张表。 测试的价值不只是「发现问题」，更是「把问题的范围缩小到一行 SQL」。
