一个合格的缺陷单，应该让开发无法反问

2026-09-12 约 6 分钟 禅道 · 抓包 · 日志

我提的第一个缺陷被开发打回了。理由是：「你描述的现象我复现不出来，请补充环境。」 点开一看，我只写了六个字：「借款金额不对」。

那一刻我明白：缺陷单不是「告诉别人有问题」，而是让对方按你的步骤，看到同样的错误。 换句话说，合格的缺陷单应该做到 —— 开发看完不需要反问任何一句话。

四个必填项

1. 环境信息

同一个页面，dev 环境和预发环境可能挂着不同的分支。至少写清：环境地址、账号、浏览器/版本、构建版本或提交号。 移动端还要加 App 版本和机型。 

环境：预发 http://pre.example.com
账号：test_user_01 / 123456
浏览器：Chrome 128 / Windows 11
版本：build-20260912-3

2. 可复现的步骤

标准是：别人照着做，能稳定看到同样的结果。所以「借款金额不对」要改成编号步骤：

  1. 用 test_user_01 登录；
  2. 进入「我要借款」，填写金额 1000，期限 3 个月，点击提交；
  3. 审核账号登录后台，审核通过；
  4. 回到用户端进入「我的借款」，查看列表中的借款金额。

偶现的问题还要补一句出现频率：10 次里出现 3 次，与网络慢时更容易出现。

3. 预期 vs 实际

这两行一定要分开写，不要混在一句话里。因为混着写，开发很容易只看懂「实际」，不知道「应该是什么」。

项内容
预期结果列表显示借款金额 1000.00 元，与提交金额一致
实际结果列表显示 100.00 元，金额少了两位（疑似单位换算错误）

4. 证据链

截图是基础，但截图只能证明「看到的」，不能证明「发生的」。我一般附三类证据：

  • 界面截图：带完整 URL 和时间的全屏图，不要只截元素；
  • 接口响应：Fiddler / Charles 抓包，看 amount 字段实际返回了什么；
  • 数据库记录：一条 SQL 加结果截图，确认到底存错了还是显示错了。

三次定界：把问题缩小到一层

缺陷单写完还不算完。真正让开发觉得「这个测试很专业」的，是你已经帮他排查过一轮。 我的顺序是固定的三步：

第一步：抓包看请求

请求里的参数对不对？如果前端传的金额本身就是 100，那是前端传参问题； 如果传的是 1000 但返回 100，问题在后端。这一步能砍掉一半的扯皮。

第二步：SQL 看数据

请求对、返回错，就去数据库看落库值。落库对但显示错 → 查询或序列化层； 落库就错 → 业务逻辑或事务层。具体写法见数据库核对那篇。

第三步：日志看堆栈

Linux 上用 grep 按 traceId 捞日志，能看到异常堆栈和耗时： 

# 按时间窗口捞错误日志
tail -n 2000 app.log | grep -i "ERROR" | grep "2026-09-12 14:2"

# 按 traceId 追踪一次完整请求
grep "traceId=8f3a91c2" app.log

把这三步的结论写成一句话放进缺陷单，比如： 「已抓包确认前端传参 1000 正确，数据库 t_loan.amount 落库为 100，疑似后端单位换算（分/元）错误。」 —— 这样开发打开单子就能直接定位文件，效率完全不同。

优先级 ≠ 严重程度

这两个字段经常被填成一样，其实判断维度不同：

看什么例子
严重程度问题本身的破坏力金额计算错误 → 严重
优先级多快需要被修错别字在首页 Banner → 严重程度低，优先级高

我的习惯是：涉及资金、权限、数据丢失的一律最高，因为它影响的是「可不可信」； 纯展示问题看曝光位置决定优先级。这样排出来的修复顺序，产品也认可。

最后一步：闭环

缺陷的生命周期不止于「已修复」。我的收尾动作有三个：

  1. 回归验证：按原步骤复现，确认现象消失；
  2. 关联回归：同一模块、同一逻辑的相邻功能再跑一遍，防止改 A 坏 B；
  3. 沉淀用例：把这个场景补进用例库，下次回归自动覆盖。
一个缺陷真正的价值，是让它不要再出现第二次 —— 而这靠的是用例沉淀，不是关闭按钮。

现在回头看那个被打回的缺陷单，我反而挺感谢它。它让我从「报 Bug 的人」变成了 「能把问题说清楚的人」—— 后者才是测试工程师的核心能力。
